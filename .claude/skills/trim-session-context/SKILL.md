# trim-session-context

このスキルの核となる語は **production residue**(会話の名残)——成果物の「何のためか」ではなく「どう作られたか」を漏らしてしまう痕跡のこと。

## Core Principle

会話は制作過程の文脈であって、成果物の中身そのものではない。成果物に残す前に、各記述を次の3つに分類する。

1. 読み手が本当に必要とするユーザー向けの内容 → そのまま残す
2. 制作上の判断(想定読者・トーン・制約) → 構成・言葉遣い・具体例に反映させ、事実として書かない
3. 会話の残りかす → 削る

## Residueの見分け方

「ご要望通り」「〜という指示なので」「以前のバージョンとは違い」「制約があるため」「Git/Homebrewは使わない」といった言い回しはResidueの目印。ただし機械的に削らず、読み手が本当にその情報を必要とするかを都度確認する。

会話で示された具体例は意図を伝えるための診断材料であり、成果物の題材そのものではない。そこから抽象度・想定読者・トーンを読み取るにとどめ、成果物自身が必要としない限り、その例自体を転記しない。

制約は宣言ではなく設計に反映させる。

悪い例:
> 本ガイドではGit・Homebrew・追加のCLIツールは使用しません。

良い例:
> プロジェクトフォルダはGoogle Driveで共有してください。

## 点検チェックリスト

- 会話を見ていない読み手にも自然に読めるか
- なぜこう書いたかを説明する一文が紛れていないか
- ツール名・除外事項・採用しなかった案への言及が残っていないか
- 会話中の具体例がそのまま成果物の題材になっていないか
- 複数回の修正の継ぎ接ぎ跡(トーン・用語・前提のブレ)がないか
- 見出しや注記は制作者ではなく読み手向けに書かれているか

## 仕上げ方

説明を加えるより書き直す。目的・技術的な正確さ・読み手が本当に必要とする要件は保持しつつ、制作上の指示は成果物の設計に変換する。

- 「高度な用語を避けて」→ 平易な言葉遣いそのものにする
- 「初心者向けに」→ 説明のペース配分・用語の定義・具体例として反映する

## 出力

仕上げた成果物そのものを渡す。必要な場合のみ短いラベルを添える。変更点の要約はユーザーが求めたときだけ、成果物の後に置く。

## 品質基準

会話を見ていない読み手が、そこにあった制作上の指示や修正のやり取りを読み取れないこと——それが成果物自身にとって本当に必要な情報である場合を除いて。
