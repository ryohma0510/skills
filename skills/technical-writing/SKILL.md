# 技術文書

人間が判断を追え、後続の AI が実装や作業に必要な情報を読み取れる技術文書にする。
既存実装の詳細を知らない読者が、何を理解して次に何を判断する必要があるかを捉えて書く。
原則を機械的に揃えることより、読者が理解するときの負担を減らすことを優先する。

## 構成 — 読む場所と、伝える内容を分ける

全体から部分、原因から結果など、情報の依存関係・因果関係に沿って説明を並べる。
要点を先に示し、その理解に前提が必要なら先に補う。
関連する前提と説明は近くへ置き、離れた節の往復や、前の情報を覚え続ける負担を減らす。

親見出しのカテゴリで読む場所を選び、子見出しでその節の結論や判断が分かる形を基本にする。
「保存時の競合制御」の下に「新旧の保存はテナント単位の行ロックで直列化する」を置くように、
子見出しはその節が答える疑問への答えにする。
一節で一つの疑問に答え、理由・条件・例外は対応する判断の近くへ置く。

カテゴリや見出しは、文書の種類と対象に合わせて選ぶ。
API の METHOD・path、Request / Response、UC・イベント名など、探すための名前は保持する。
必要な説明をその下に置き、すべての節を同じ階層へ揃える必要はない。
プロジェクトの文書テンプレート（設計書・API リファレンスなど）の必須見出し・表の列・図・ID の契約を優先する。

詳細度は、人間の判断と AI による実装・再現に必要かどうかで決め、どちらにも寄与しない詳細を削る。
重要な選択には理由と影響を添え、単純な変更は簡潔に記す。
比較や契約の一覧には表、並列の項目には箇条書き、因果の説明には文章など、理解しやすい形を選ぶ。
同じ内容は原則として一か所へ集める。理解を助ける近接した短い再提示は許容し、
重複を避けるためだけに読者を参照先へ往復させない。

## 文章 — 一つの考えを、条件と一つに伝える

文の中心を一つにする。別の主張に移るところで文を分け、段落は一つの論点を要点から説明する。
条件・結果・理由が一つの判断を伝える場合は、つながりを保つ。
分割後も「停止中なら」などの条件がどの処理まで掛かるかを明確にする。
文字数や段落数ではなく、一度に追う必要のある考えの数を手掛かりにする。

重要な条件や例外は本文で読めるようにする。
長い括弧の補足は対応する文や段落へ移し、短い用語の補足などは読みやすければ残す。
コードに対応する概念は実際の識別子で示し、初出で役割を説明する。
参照できるコードへのリンクは permalink を使い、既存の file:line 契約も守る。

判断の内容・理由・条件を本文に残し、R6 / R14 のような検討メモの番号は完成本文から原則外す。
API 番号・不変条件 ID・必要な要件トレース・既存 symbol の file:line は保持する。
根拠の参照はどの主張に対応するか分かる形で節末などへまとめる。
参照の配置に既存の契約があればそれに従い、機械的な一括移動はしない。

## 仕上げ — sanitize-doc

構成と文章の原則で本文を書き終えたあと、対象ファイルに対して Skill ツールで `sanitize-doc` を発動する。
語彙の平易化・装飾文言・会話の名残の点検基準は `sanitize-doc`（およびその内部の `plain-vocab` / `trim-ai-smell` / `trim-session-context`）に任せ、このスキルでは重ねて定義しない。

完了条件: `sanitize-doc` の一連の適用が終わっている。

## 例 — 括弧から仕様を取り出す

設計書向けの例。停止中の旧画面からの保存仕様を説明する。

推敲前:

> 停止中の貸方: 画面の追加・編集は、送られた空でない貸方を拒否せずに捨て、ほかの項目を保存する（新しいエラー種別は作らない。R6）。捨てたことは200の応答のdiscardedFieldsで返し、画面はトーストで伝える（R14。api.md）。

推敲後:

> 停止中に旧画面から追加・編集するときは、貸方に値が入っていても、その値を保存しない。他の項目は保存する。
>
> 応答は200とし、無視した項目を discardedFields で返す。画面は保存結果をトーストで伝える。
>
> この処理のための新しいエラー種別は設けない。

「停止中なら、画面保存の貸方を捨て、旧CSVの貸方入力も拒否する」を分ける場合は、
両方に停止中という条件が掛かることが分かるように書く。
短文への分割で条件の範囲を変えない。

## 適用と確認

生成時は読者の疑問から構成し、更新時は担当する分冊と関連する正本を照合する。
書き終えたら、節ごとに伝える判断・理由・条件を捉え直し、本文を組み立て直す。
括弧内に独立した説明があれば、対応する文や段落へ戻す。
判断を探せるか、文と段落を自然に追えるかを確かめる。
元の仕様・要件と照合し、条件・例外・API 契約・未決事項が残り、確定度が変わっていないことまで確認する。
読みやすさの編集で不足する内容を推測して補わず、未決は未決として扱う。

## レビュー

レビュー時も同じ構成・文章の原則を使い、誤解する箇所とその理由を具体的に指摘する。
内容の正しさ・レビューの重大度は、その文書種別の既存レビュー基準に従う。
このスキル専用のレビュアーや、全変更の Before / After 報告は追加しない。
図の追加・改善方針はこのスキルでは定めず、既存テンプレートの作図指示を使う。

## 原則の出典

要点はこの `SKILL.md` に含めているため、実行のたびに外部取得する必要はない。
詳しい説明が必要なときは [references/sources.md](references/sources.md) を参照する。
英語固有の文法ルールは日本語へそのまま適用しない。
用語の判断に迷う場合の公的資料は `plain-vocab` スキル（`sanitize-doc` 経由でも到達する）を参照する。
