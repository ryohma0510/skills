# テスト駆動開発

TDD は red → green のループである。このスキルはループの回し方を定める——ループに入る前に何を確定し、1サイクルでどこまでやり、何をループの外に置くか。**何が良いテストかは `test-design` スキルを参照すること。**

すべてのセクションは毎サイクル適用される——ループの前と最中に参照すること、後ではない。

コードベースを探索するときは `CONTEXT.md`（存在すれば）を読み、テスト名とインターフェースの語彙がプロジェクトのドメイン言語と一致するようにすること。また、触れている領域の ADR を尊重すること。

## 1. seam を確定する

テストを書く前に、テスト対象の **seam**（振る舞いを観測する公開境界）を書き出し、ユーザーに確認すること。

「公開インターフェースは何で、どの seam をテストすべきか？」と問うこと。

seam の定義と選び方は `test-design` スキルを参照。

**完了条件**: テスト対象の seam を列挙し、ユーザーが明示的に合意した。暗黙の了解は未完了として扱う。

## 2. red——失敗するテストを書く

合意した seam のうち1つについて、テストを1本書く。

**完了条件**: テストを実行し、期待した理由で失敗することを確認した。テストが存在するだけでは未完了とする。

## 3. green——通すコードだけを書く

いま red になっているテスト1本を green にするコードだけを書く。

**完了条件**: そのテストが通ることを実行して確認した。既存テストスイート全体の事前実行はCIに任せ、ローカルでは対象のテストのみを実行する。

リファクタリングはレビュー段階（`code-review` スキル）で行う。red → green の実装サイクルには含めない。

## vertical slice で進める

1サイクルにつき、1つの seam、1つのテスト、1つの最小実装。1テスト → 1実装 → 繰り返しと進め、各テストを **tracer bullet** ——直前のサイクルが教えてくれたことに応答する一発——として扱うこと。

テストをまとめて先に書いてから実装をまとめて書くと、_想像上の_振る舞いを検証することになる: ユーザーから見える振る舞いではなく物事の_形_をテストしてしまい、テストは実際の変更に鈍感になり、実装を理解する前にテスト構造にコミットしてしまう。
