名前は、読み手が実装を読む前に手にする唯一の手がかりであることが多い。

## 原則

名前は指すものを過不足なく指す —— これが `精度`。
名前の長さは有効範囲の広さに比例する —— これが `スコープ比例`。

## 精度

名前が指す実体を一文で言えるようにしてから名前を選ぶ。言えないなら、迷っているのは名前ではなく設計である。

実体より広い名前は情報を運ばない(`data` `info` `handle` `process` `manager`)。実体とずれた名前は読み手を誤らせる —— 単数と複数、真偽値の極性、`get`(安価な取得)と `fetch`(I/O を伴う)のような語の含意まで実装と一致させる。

精度とは具体的な語を選ぶことであり、語を増やすことではない。

汎用的な名前しか思いつかないときは、その識別子が複数の責務を抱えている兆候である。名前を捻り出すより分割したほうが、両方の名前が決まる。

## スコープ比例

定義と使用が同時に目に入るなら短い名前で足りる。ファイルをまたぎ、モジュールの外から呼ばれるものほど、名前だけで意味が立つ長さが要る。3 行のループ変数は `i` でよく、公開 API の引数は呼び出し側が定義を見ないことを前提にする。

文脈が既に与えている情報は名前から落とす。`User` クラスの中の `userName` は `name` でよい。

## 一貫性

新しい語を導入する前に、同じ概念が既に別の名前で存在しないかコードベースを検索する。同じ概念には同じ語を、異なる概念には異なる語を割り当てる。`fetchUser` と `getUser` と `loadUser` が同居するコードベースでは、読み手は毎回、存在しない違いを探すことになる。

## アンチパターン

- **曖昧** — 実体より広く、情報を運ばない名前。
- **冗長** — スコープや文脈に対して長い。文脈の再掲、型名の埋め込み(`userList: List<User>`)。
- **不正確** — 名前が実態と食い違う。単数・複数、真偽値の極性、語の含意のずれ。実装の変更に取り残された名前もここに含む。
- **不統一** — 同じ概念に別の語、または別の概念に同じ語。
- **混在** — 英語に置き換えられる語をローマ字のまま使っている(`kingaku` `torihikisaki`)。

## 慣習

周囲のコード・言語・フレームワークの慣習が原則に優先する。React の `use*`、Go の短いレシーバ名、フレームワークが要求する名前は、従うこと自体が読み手への情報になる。原則は、慣習が何も言っていない場所で効く。

## 記述言語

英語で命名する。訳すと意味や検索性が壊れる固有語 —— 法令名・制度名・社内の業務用語・外部 API が定める語 —— は原語(ローマ字を含む)のまま使う。

## コードを変更するとき

変更したコードの名前は直す。変更していない箇所の名前は指摘に留め、リネームの指示を待つ。リネームは差分を膨らませ、レビューの焦点をずらす。

## 適用範囲

自動生成コードは対象外。テストコード内の識別子は対象だが、テスト関数名の形式は `test-design` が定める。

## 既存の名前を評価するとき

`曖昧` `冗長` `不正確` `不統一` `混在` のラベルを頭に付けた箇条書きで、`file:line` とともに指摘する。修正はユーザーの指示を待つ。

## 書き終えたら

新しく導入した名前すべてを 5 ラベル(`曖昧` `冗長` `不正確` `不統一` `混在`)で自己点検し、不合格のものを直してから完了とする。周囲のコードに倣っただけでは点検したことにならない。
