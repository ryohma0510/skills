# Push & PR 作成

変更を push し、draft PR を作成する。タイトルと description は **承認ゲート**（ユーザーが明示的に承認した状態）を通ってから PR になる。

## 1. push

```bash
git push -u origin $(git branch --show-current)
```

完了条件: リモートに現在のブランチが存在する。

## 2. base ブランチの決定

引数で base が指定されていればそれを使い、このステップを終える。

指定がなければ、リモートを最新化して直接の親ブランチを推定する。

```bash
git fetch --prune
```

候補を一覧する（自分自身は除外）。

```bash
git branch -r --format='%(refname:short)' | sed 's|origin/||' \
  | grep -E "^(develop|topic)/" | grep -v "^$(git branch --show-current)$"
```

各候補について merge-base から HEAD までのコミット数を数え、最小の候補を親とみなす。候補がなければ `main` をデフォルトにする。

```bash
git rev-list --count $(git merge-base HEAD origin/<candidate>)..HEAD
```

デフォルト候補を **AskUserQuestion** で提示する: 「base ブランチは `<候補>` でよいですか？ 別のブランチを指定する場合は入力してください」

完了条件: ユーザーの回答で base が1つに確定している。

## 3. diff の取得

```bash
git log <base>...HEAD --oneline
git diff <base>...HEAD --stat
git diff <base>...HEAD
```

完了条件: 全変更ファイルの diff を読み終えている。

## 4. タイトルの生成

diff の内容から日本語で生成する。50文字以内を目安に、変更の目的と内容を端的に表す。

## 5. テンプレートの選択

リポジトリの PR テンプレートを探す。

```bash
ls .github/pull_request_template.md .github/PULL_REQUEST_TEMPLATE.md \
   PULL_REQUEST_TEMPLATE.md docs/pull_request_template.md \
   .github/PULL_REQUEST_TEMPLATE/ 2>/dev/null
```

見つかったテンプレートをすべて読み、**AskUserQuestion** で1回だけ聞く。選択肢は、見つかったテンプレート各ファイル（`.github/PULL_REQUEST_TEMPLATE/` に複数ある場合はファイル別に並べる）と、このスキルのテンプレート。

リポジトリのテンプレートを選んだ場合は、その見出し構成を骨格にして各セクションを diff の内容で埋める。テンプレートが記入方法を明示している項目はその指示に従い、指示のない部分だけ次のステップのガイドラインを適用する。図解と末尾の `🤖 Generated with [Claude Code](https://claude.com/claude-code)` 行は、どちらのテンプレートでも入れる。

完了条件: 使うテンプレートが1つに決まっている。

## 6. Description の生成

diff を分析し、以下のテンプレートで日本語の description を書く。設計判断や背景の「なぜ」を軸にし、コードの羅列ではなく意図が伝わる記述にする。リポジトリのテンプレートを選んだ場合は、以下のテンプレート本体の代わりにそちらの見出しを使い、後続のガイドラインはテンプレートの指示がない部分にだけ適用する。

```markdown
## Summary

（変更の背景・目的を 2〜3文以内の自然文で説明）

<!-- 図解（Mermaid / ASCII アート / 画像）をここに含める -->

### 設計判断

（判断がない単純な変更ではセクションごと省略）

## レビュー観点

- 観点1
- 観点2

## 動作確認

- [ ] 確認項目1
- [ ] 確認項目2

## リリース時に確認すること

（main マージ後・デプロイ後にのみ確認できる項目。該当なしの場合はセクションごと省略）

- [ ] 確認項目1

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

### 全体方針

description を書き上げたら、Skill ツールで `doc-trim` を発動し、生成した本文に適用してから次のステップへ進む。承認ゲートで修正したときも同じく適用してから提示し直す。

レビュアーが読む気を失わない簡潔さを優先する。変更ファイル・追加行数など diff から読み取れる情報は GitHub の Files Changed に任せ、description には書かない。「主な変更点」「変更一覧」「変更ファイル」といった列挙セクションも同じ理由で置かない。

### Summary

- 2〜3文以内の自然文で、背景と目的のみを書く。
- 図解を含める。省略してよいのは、図解化する情報量がない単純変更（タイポ、文言修正、単一ファイルのリネーム等）のみ。
  - インフラ構成・データフロー・Pub/Sub 等のメッセージング・コンポーネント関連・状態遷移・非同期処理のシーケンス → ASCII アートまたは Mermaid を生成する。
  - 画像の方が適する場合（UI 変更、既存の設計図があるケース等）→ `<!-- ここに画像を貼ってください -->` プレースホルダを入れ、ユーザーに貼付を促す。
- ブランチ名から関連チケット（例: ABC-123）が特定できる場合は Summary 内で言及する。

### 設計判断

書き分けと記述例は [`references/design-decisions.md`](references/design-decisions.md) を読んでから書く。

### 長大な添付

- 動作確認の根拠になる terraform plan やコマンド実行結果は `<details>` タグで畳んで貼る（「動作確認」セクションのチェック項目の直下が目安）。
- 設計判断や背景説明のために必要な出力も `<details>` で畳む。
- それ以外の補足的な長文出力（参考情報レベルのログ等）は、レビュアーから要求されたときに貼る。

### 動作確認 / リリース時に確認すること

- チェックボックス形式で、手動での確認が必要な項目のみを書く。ユニットテスト・lint・フォーマット・型チェックなど CI が自動で見る項目は CI に任せる。
- 「動作確認」: この PR 内で確認できる項目（例: terraform plan の結果確認、ローカルでの動作確認）。
- 「リリース時に確認すること」: main マージ後・デプロイ後にのみ確認できる項目（例: terraform apply 後の動作確認）。該当項目がなければセクションごと省略する。

### レビュー観点

副作用・パフォーマンス・エッジケース・命名・セキュリティといった一般的な指摘は AI レビューが拾うため、ここには人間の判断が要る点だけを挙げる。

- 実装中に迷った設計判断と、その分岐点（別案を採る余地が残っているもの）
- 後から変えにくい決定（インターフェース、データ構造、責務の境界）

作業中の会話で迷いが出た判断があれば、それを優先して挙げる。該当がなければセクションごと省略する。

完了条件: テンプレートの各セクションが、埋まっているか意図的に省略されているかのどちらかになっている。

## 7. 承認ゲート

タイトルと description の全文を **AskUserQuestion** で提示する: 「この内容で PR を作成してよいですか？ 修正したい箇所があれば指示してください」

修正指示があれば反映し、修正後の全文を再度 **AskUserQuestion** で提示する。これを繰り返す。

完了条件: 直前に提示した全文に対して、ユーザーが明示的な承認（「OK」「いいよ」「作成して」等）を返している。この状態に達したときにだけ次のステップへ進む。

## 8. PR の作成

draft で作成する。

```bash
gh pr create --draft --base <base> --title <title> --body <body> --assignee @me
```

## 9. 結果の報告

PR URL、base ブランチ、タイトルを報告する。
