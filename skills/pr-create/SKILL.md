# Push & PR 作成

変更を push し、draft PR を作成する。ユーザーがタイトルと description を承認するまで PR は作らない。

## 1. push

```bash
git push -u origin $(git branch --show-current)
```

## 2. base ブランチの決定

引数で base が指定されていればそれを使い、このステップは飛ばす。

指定がなければ、リモートを最新化して直接の親ブランチを推定する。

```bash
git fetch --prune
```

候補を一覧する（自分自身は除外）。

```bash
git branch -r --format='%(refname:short)' | sed 's|origin/||' \
  | grep -E "^(develop|topic)/TDL-" | grep -v "^$(git branch --show-current)$"
```

各候補について merge-base から HEAD までのコミット数を数え、最小の候補を親とみなす。

```bash
git rev-list --count $(git merge-base HEAD origin/<candidate>)..HEAD
```

候補が見つからなければ `main` をデフォルトにする。

決まったデフォルト候補を **AskUserQuestion** で提示し、「base ブランチは `<候補>` でよいですか？ 別のブランチを指定する場合は入力してください」と確認する。ユーザーの回答で base を確定する。

## 3. diff の取得

```bash
git log <base>...HEAD --oneline
git diff <base>...HEAD --stat
git diff <base>...HEAD
```

## 4. タイトルの生成

diff の内容から日本語で生成する。50文字以内を目安に、変更の目的と内容を端的に表す。

## 5. Description の生成

diff を分析し、以下のテンプレートで日本語の description を書く。設計判断や背景の「なぜ」を軸にし、コードの羅列ではなく意図が伝わる記述にする。

```markdown
## Summary

（変更の背景・目的を 2〜3文以内で説明。箇条書き禁止）

<!-- 図解（Mermaid / ASCII アート / 画像）をここに含める -->

### 設計判断

（代替案との比較がある場合は表形式、既存パターン踏襲など比較対象がない判断は短文で記述。設計判断がない単純な変更ではセクションごと省略）

## レビュー観点

- 観点1
- 観点2

## 動作確認

- [ ] 確認項目1
- [ ] 確認項目2

## リリース時に確認すること

（main マージ後・デプロイ後にのみ確認できる項目。該当なしの場合はセクションごと省略）

- [ ] 確認項目1

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

### 全体方針

レビュアーが読む気を失わない簡潔さを優先する。diff から読み取れる情報（変更ファイル・追加行数など）は書かない。

「主な変更点」「変更一覧」「変更ファイル」といった変更点の列挙セクションは作らない。変更点は GitHub の Files Changed で確認できるため、description に書くと二重情報になる。

### Summary

- 2〜3文以内、箇条書き禁止。背景と目的のみを自然文で書く。
- 図解を原則必須で含める。省略してよいのは、図解化する情報量がない単純変更（タイポ、文言修正、単一ファイルのリネーム等）のみ。
  - インフラ構成・データフロー・Pub/Sub 等のメッセージング・コンポーネント関連・状態遷移・非同期処理のシーケンス → ASCII アートまたは Mermaid を生成する。
  - 画像の方が適する場合（UI 変更、既存の設計図があるケース等）→ `<!-- ここに画像を貼ってください -->` プレースホルダを入れ、ユーザーに貼付を促す。
- ブランチ名から関連チケット（例: TDL-413）が特定できる場合は Summary 内で言及する。

### 設計判断

代替案との比較がある決定は表にする。列は `選択肢 / 採用 / 理由`。複数のテーマにまたがる場合は、テーマごとに `####` 見出し + 個別の表に分ける（`テーマ / 選択肢 / 採用 / 理由` の4列で1つの表にまとめない）。

```markdown
#### Trace伝搬形式

| 選択肢                                   | 採用 | 理由                                                                     |
| ---------------------------------------- | ---- | ------------------------------------------------------------------------ |
| X-Cloud-Trace-Context文字列              | -    | 本体旧形式。ジョブには既にOTelベースの`withTraceContext`があるため不一致 |
| W3C traceparent (OTel Propagator inject) | ✅   | tenant-task-dispatcherと揃い、ジョブのOTel基盤と整合性が高い             |

#### エミュレータ接続方式

| 選択肢                               | 採用 | 理由                                                                      |
| ------------------------------------ | ---- | ------------------------------------------------------------------------- |
| ManagedChannelBuilder + 手動shutdown | -    | 旧実装。Publisher毎のcloseコールバック管理が必要                          |
| InstantiatingGrpcChannelProvider     | ✅   | tenant-task-dispatcherの最新パターン。ライフサイクル管理をgaxに任せられる |
```

比較対象のない方針選択・既存パターン踏襲は、見出し + 本文2文以内で書く。表にすると内容がスカスカになるため使わない。

```markdown
### IAM はプロジェクトレベル付与

`invoice-line` 等の既存パターンに倣う。
```

### 長大な添付

- 動作確認の根拠になる terraform plan やコマンド実行結果は `<details>` タグで畳んで貼る（「動作確認」セクションのチェック項目の直下が目安）。
- 設計判断や背景説明のために必要な出力も `<details>` で畳む。
- それ以外の補足的な長文出力（参考情報レベルのログ等）は、レビュアーから要求された場合にのみ貼る。

### 動作確認 / リリース時に確認すること

- チェックボックス形式で、手動での動作確認が必要な項目のみを書く。CI で自動チェックされる項目（ユニットテスト、lint、フォーマット、型チェック等）は含めない。
- 「動作確認」: この PR 内で確認できる項目（例: terraform plan の結果確認、ローカルでの動作確認）。
- 「リリース時に確認すること」: main マージ後・デプロイ後にのみ確認できる項目（例: terraform apply 後の動作確認）。該当項目がなければセクションごと省略する。
- diff だけでは適切な手動確認項目を判断できない場合は、**AskUserQuestion** でユーザーに確認する。

### レビュー観点

diff を分析し、レビュアーが重点的に確認すべきポイントのみを記載する。該当するものだけを挙げ、なければ省略する。

- 既存ロジックへの影響範囲や副作用
- パフォーマンスへの影響
- エッジケースの考慮漏れ
- 命名やインターフェース設計の妥当性
- セキュリティ上の懸念
- 変更が大きい箇所や複雑なロジックの正当性

## 6. ユーザー承認

生成したタイトルと description の全文を **AskUserQuestion** で提示し、「この内容で PR を作成してよいですか？ 修正したい箇所があれば指示してください」と確認する。

修正指示があれば反映し、修正後の全文を再度 **AskUserQuestion** で提示する。ユーザーが明示的に承認（「OK」「いいよ」「作成して」等）するまでこのループを繰り返す。承認を得てから次のステップへ進む。

## 7. PR の作成

draft で作成する。

```bash
gh pr create --draft --base <base> --title <title> --body <body> --assignee @me
```

## 8. 結果の報告

PR URL、base ブランチ、タイトルを報告する。
