# Description の書き方

## テンプレート

```markdown
## Summary

（変更の背景・目的を 2〜3文以内の自然文で説明）

<!-- 図解（Mermaid / ASCII アート / 画像）をここに含める -->

## 関連 PR

（スタックに属さない単独の PR ではセクションごと省略）

| 順 | PR |
| --- | --- |
| 1 | https://github.com/owner/repo/pull/12 |
| 2 | https://github.com/owner/repo/pull/13 👈 このPR |
| 3 | https://github.com/owner/repo/pull/14 |

## 設計判断

（判断がない単純な変更ではセクションごと省略。重点的に見てほしい判断の見出しには 🚨 重点レビュー を付ける）

## 動作確認

- [ ] 確認項目1
- [ ] 確認項目2

🤖 Generated with AI
```

## ガイドライン

### 全体方針

レビュアーが読む気を失わない簡潔さを優先する。変更ファイル・追加行数など diff から読み取れる情報は GitHub の Files Changed に任せ、description には書かない。「主な変更点」「変更一覧」「変更ファイル」といった列挙セクションも同じ理由で置かない。

description は最後の状態だけを書く。セッション中に方針を変えた・実装を差し替えたといった経緯は、レビュアーが読むのが今の差分である以上、書かない。更新モードで既存 PR の本文を書き換えるときも、前の本文に追記するのではなく最新の差分から書き直す。

その過程で下した判断のうち、後から変えにくいもの・別案を採る余地が残るものは「設計判断」に残す。採用しなかった案を書くのは、時系列の記録としてではなく、レビュアーが判断の妥当性を検討できるようにするため。

### Summary

- 2〜3文以内の自然文で、背景と目的のみを書く。
- 図解を含める。省略してよいのは、図解化する情報量がない単純変更（タイポ、文言修正、単一ファイルのリネーム等）のみ。
  - インフラ構成・データフロー・メッセージング・コンポーネント間の関連・状態遷移・非同期処理のシーケンス → ASCII アートまたは Mermaid を生成する。
  - 画像の方が適する場合（UI 変更、既存の設計図があるケース等）→ `<!-- ここに画像を貼ってください -->` プレースホルダを入れ、ユーザーに貼付を促す。
- ブランチ名から関連チケット（例: ABC-123）が特定できる場合は Summary 内で言及する。

### 関連 PR

- 列は `順 / PR` の2列。base・head・状態は PR ページで見られるうえ変わるため書かない。
- PR 列には URL をそのまま貼る。GitHub がタイトルとマージ状態を補って表示するため、こちらでタイトルを書き写すと古くなる。装飾（太字やリンクテキスト）を付けるとこの展開が効かなくなる。
- スタックの根（base が既定ブランチのもの）から先端へ向かって並べる。
- このPRの行は URL の後ろに `👈 このPR` を添える。レビュアーが自分の位置を見失わないようにするための行。
- スタックに属さない単独の PR ではセクションごと省略する。

### 設計判断

重点的にレビューしてほしい判断は、見出しを `### 🚨 重点レビュー: <テーマ>` の形にする。副作用・パフォーマンス・エッジケース・命名・セキュリティといった一般的な指摘は AI レビューが拾うため、この印を付けるのは次のような人間の判断が要るものに絞る。

- 実装中に迷った判断（別案を採る余地が残っているもの）
- 後から変えにくい決定（インターフェース、データ構造、責務の境界）

#### 代替案との比較がある決定 → 表

列は `選択肢 / 採用 / 理由`。テーマが複数あるときは、テーマごとに `###` 見出し + 個別の表に分ける（`テーマ / 選択肢 / 採用 / 理由` の4列で1つの表にまとめると、どの判断がどこで効いているか読めなくなる）。

```markdown
### 🚨 重点レビュー: リトライ方式

| 選択肢                   | 採用 | 理由                                                     |
| ------------------------ | ---- | -------------------------------------------------------- |
| 呼び出し側で固定回数実装 | -    | 呼び出し箇所ごとに実装が散り、間隔の調整が効かない       |
| クライアント層で指数バックオフ | ✅ | 呼び出し側は設定のみで済み、既存の HTTP クライアントと揃う |

### 設定値の受け渡し

| 選択肢               | 採用 | 理由                                             |
| -------------------- | ---- | ------------------------------------------------ |
| 環境変数を直接参照   | -    | テストで差し替えられず、必須値の欠落も実行時まで出ない |
| 起動時に設定オブジェクトへ束ねる | ✅ | 起動時に検証でき、テストからも値を注入できる     |
```

#### 比較対象のない方針選択・既存パターン踏襲 → 見出し + 本文2文以内

```markdown
### 権限付与はプロジェクトレベル

同じ構成の既存モジュールに倣う。
```

### 長大な添付

- 動作確認の根拠になるコマンド実行結果（dry-run や plan 系の出力など）は `<details>` タグで畳んで貼る（「動作確認」セクションのチェック項目の直下が目安）。
- 設計判断や背景説明のために必要な出力も `<details>` で畳む。
- それ以外の補足的な長文出力（参考情報レベルのログ等）は、レビュアーから要求されたときに貼る。

### 動作確認

- チェックボックス形式で、手動での確認が必要な項目のみを書く。ユニットテスト・lint・フォーマット・型チェックなど CI が自動で見る項目は CI に任せる。
- この PR 内で確認できる項目を書く（例: dry-run の結果確認、ローカルでの動作確認）。
